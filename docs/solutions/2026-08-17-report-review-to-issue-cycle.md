# Задача Issue-агента застревала в фазе «PR открыт» — ревью-агент не докладывал о своей работе

## Ситуация

Контур задач держит каждую задачу живым workflow'ом: после открытия PR задача переходит в фазу `pr-open` и ждёт. Работу делал ревью-агент, но никто не сообщал контуру о её завершении — задача оставалась в `pr-open` навсегда, статус-доска врала.

## Причина

Разделение ответственности было строгим: свои вебхуки по PR контур задач не слушает намеренно — фазу двигает тот, кто выполнил работу, а не тот, кто мимо проходил. А у ревью-агента не было канала доклада: завершённое ревью публиковалось в PR и на этом заканчивалось, в контур задач не попадало ничего.

## Решение

Добавлен конверт доклада `reliability/agent_event.py`: `POST /agent-event` с HMAC-подписью, фаза `pr-review`, ключ задачи извлекается из `Closes #N` в теле PR (`github_client.get_pull_body`). Worker докладывает после ack по `/review` (`started`) и при dead-letter (`failed`). Канал выключается целиком, если env `ISSUE_AGENT_URL`/`AGENT_EVENT_SECRET` пусты.

Границы заложены в дизайн: `/describe` фазу не двигает (переписывает описание PR — это не та работа, о которой докладывают как о ревью); `skipped` не докладывает (ревью сделал сиблинг — он и докладывает); несколько `Closes #N` в теле оставляют ключ пустым (выбрать первый попавшийся — привязать работу не к той задаче и испортить трассировку сразу двум). Доклад никогда не роняет обработку: ревью уже опубликовано, обменивать сделанную работу на несделанный доклад нельзя — при сбое доклада задача продолжается, а событие уходит в лог.

## Как проверить

```
cd self-hosted && python3 -m unittest reliability.tests.test_agent_event -v
```

187 тестов всего (было 173). Вживую: открыть PR с `Closes #N` и дождаться `/review` — задача в контуре переходит из `pr-open` в `pr-review`.

## Уроки

- «Фазу двигает исполнитель работы, а не свидетель» — принцип, который экономит часы дебага границ ответственности между автоматами.
- Обратный канал статусов между двумя автоматами обязан быть выключаемым и не обязан быть надёжным «в обе стороны»: потерянный доклад не должен ронять основную работу.
