# Бот слал 5× «Preparing review…» — лестница таймаутов рвала вызовы LLM и плодила дубли

## Ситуация

В PR появлялось по пять дублей комментария «Preparing review…». Каждое ревью, которое могло бы завершиться, обрывалось и запускалось заново; пользователь видел несколько одинаковых заглушек вместо одного результата.

## Причина

Дефолт `CONFIG_AI_TIMEOUT=90с` был меньше реальной длительности вызова LLM (~272с на один проход). Каждый такой вызов падал в `GatewayUnavailable`, очередь ретраила (`max_attempts=5`), а reconcile-свипер до-энквеливал задачу заново — три механизма ретрая наслаивались друг на друга. Отдельно: `visibility_timeout` очереди был захардкожен `120` без env-ручки, поэтому поднятый `task_timeout` молча превышал его — очередь передоставляла ещё идущее ревью, получался конкурентный дубль.

## Решение

LLM-кап поднят до 10 минут, все слои таймаута вынесены в `.env`:

| VAR | было | стало |
|---|---|---|
| `CONFIG_AI_TIMEOUT` | 90 | `600` |
| `RELIABILITY_ATTEMPT_TIMEOUT` | 75 | `630` |
| `RELIABILITY_TASK_TIMEOUT` | 90 | `660` |
| `RELIABILITY_VISIBILITY_TIMEOUT` | нет ручки, хардкод 120 | `720` |

В `worker.py` добавлен `resolve_timeouts()`: читает все четыре слоя из env и на старте fail-fast (`ValueError`) проверяет инвариант `CONFIG_AI ≤ ATTEMPT < TASK < VISIBILITY` — устаревший `.env` больше не может молча ломать порядок. `main()` пробрасывает `visibility_timeout` в `run_forever` (раньше туда шёл хардкод 120).

## Как проверить

```
cd self-hosted && python3 -m unittest reliability.tests.test_worker -v
```

14 passed, включая 4 теста на резолвер (дефолты держат инвариант, валидный override, устаревший `.env` падает, `task ≥ visibility` падает). Вживую: после деплоя дубли «Preparing review…» не появляются, в журналах нет `GatewayUnavailable` по таймауту.

## Уроки

- Четыре слоя таймаута (LLM-вызов ≤ попытка < задача < visibility) — это инвариант, а не четыре независимые ручки: рассинхрон любого слоя превращает ретрай-механизмы в генератор дублей.
- Таймаут лечит симптом; корень — медленный провайдер + его rate-limit, это решается отдельно (тиринг моделей, см. кейс о переходе ревьюера на более дешёвую модель).
- Если значение захардкожено рядом с настраиваемыми соседями — это мина: рано или поздно кто-то поднимет ручку выше хардкода и получит тихий баг.
